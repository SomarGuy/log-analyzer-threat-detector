      ┌─Why I built this─┐

      I'm a CS student in Toronto and I'm teaching myself forensics and security on the side. I kept reading that a SIEM "correlates logs" and I never really understood what that meant, so I wrote a small one to find out where it hurts.

      The thing that surprised me most was brute force versus password spraying. I figured they'd look the same, since both are a pile of failed logins. They aren't. Brute force is one IP hammering a few accounts. Spraying is one IP trying a couple of passwords on lots of accounts. My first spray rule also fired during the first minute of a loud brute force, because early on every account had only been tried once or twice. I only noticed because I wrote a test that replays the attack. The fix was to judge the whole attack instead of the ramp-up.

      What I'd improve: every log here is fake and written by me, so 12 out of 12 only proves the rules do what I told them to. I want to try it on logs from a throwaway VM I control. It also needs a per-user idea of normal instead of fixed office hours, proper timezone handling, and a way to catch slow attacks, because a few tries an hour walks right past it.

      The tail above is a replay of the synthetic events, not a live feed. I just like how it feels to watch.

      How to use this

      What this is

      A small log analyzer I wrote. It reads three kinds of logs (Linux SSH logins, Windows Security events and web server access logs), flags suspicious patterns, and says what to do next. A SIEM does the same job at a much bigger scale, and I built this one to find out what "correlating logs" actually means. All the data here is synthetic, so nothing you click touches a real system.

      Try this in 60 seconds

      1. Click the "critical" bar in the four coloured bars at the top. The alert list drops from 30 alerts to the 6 that would need someone right now. Notice "6 of 30 shown" above the list. Click the bar again to switch the filter off.
      2. Click the row "SQL injection probes" (rule WEB-002). A panel opens (on the right on a desktop, full screen on a phone). Notice the plain-English "What happened", the raw log lines under "Evidence", and the numbered "Recommended response". That is what an on-call person needs.
      3. In that panel, find "Part of INC-03" and click "Show only this incident". Three alerts remain, all from one IP address: a scanning tool, then SQL injection, then script injection. Separate alerts have become one story.
      4. Click "Reset", then click INC-02 in the Incidents box. Nine alerts show up. Click the "First seen" column title to read them in time order: password spraying, a login that works, encoded PowerShell, a new admin account called helpdesk_tmp. That is one break-in from start to finish.
      5. Look at the Event tail near the timeline. It replays the log lines behind the alerts. Click "pause" to stop it. It is a replay of the sample data, not a live feed.
      6. Scroll down to the MITRE ATT&CK table and click the row for T1110.003. The list filters to the two password spraying alerts. Press ? any time for the keyboard shortcuts (j and k move between alerts, Enter opens one).

      Words you will see

      Log
      A diary a computer keeps: who logged in, what was requested, what failed.
      Alert
      One thing my rules flagged as suspicious, with the evidence behind it.
      Incident
      Several alerts grouped together because they share a source IP, or a machine and a time window.
      Severity
      How urgent an alert is: critical, high, medium or low.
      Source IP
      The network address a request came from. Addresses here are reserved for examples, so none are real.
      Brute force
      One source guessing passwords over and over on a few accounts.
      Password spraying
      One source trying a couple of common passwords on lots of accounts, so no single account looks hammered.
      Off-hours login
      A login outside normal working hours, which is worth a second look.
      SQL injection
      Typing database commands into a web form or URL to trick a site into leaking data.
      XSS (cross-site scripting)
      Sneaking script code into a web page so it runs in another visitor's browser.
      Path traversal
      Using ../ in a web address to reach files that should be off limits.
      Living off the land
      An attacker using tools already on the machine (like certutil or net.exe) so there is nothing new to detect.
      MITRE ATT&CK
      A public catalogue of attacker techniques, each with an ID like T1110. I tag every alert with the ones that apply.
      Event tail
      The scrolling log at the top right. Named after the tail command that follows a log file.
